# 对 Gemini v0.1.1 固定基线审查的处理（v0.2.0）

审查对象是3cccb129dd92a77ea4085c73b159741a08603b04。Gemini声明未运行Windows/摄像头，属于静态建议，不直接视为复现。用户随后给出的真实动作失败与本机两份JSONL是独立证据。

| 意见 | 处理 | 理由与证据 |
|---|---|---|
| close幂等、单模型关闭异常不阻断另一模型 | 接受并调整 | 两模型各尝试一次，异常记录，保留初始化原错；新增测试。没有照抄空except吞错误；native失败时不提前清掉模型缓冲 |
| 清单损坏/缺字段统一可读错误 | 接受 | JSON结构、SHA256、非空数据和可选字节长度均在native创建前检查；畸形清单负例 |
| resources.root目录假设 | 不重构 | 当前_MEIPASS与源码路径实际可用，中文安装/解压测试覆盖；推测不作为已发现故障 |
| 缺模型冒烟也传干净PATH、记录安装位置 | 接受 | 同一isolated_env，记录中文路径和长度，不只改变工作目录 |
| 重试未重启 | 部分接受 | 旧代码确实会重建停止的管线，不能说完全不重启；修复了重试保留视频源、自动启用和错误时禁用暂停/校准（含空格） |
| 6.26秒关闭、分项计时 | 接受数据与计时，拒绝猜原因 | 增加采集/推理距退出请求的耗时。旧6.26秒真实；未凭日志推定必然是某后端。继续异步等待，不强杀或无证据重写为进程 |
| 握臂确认不能全程要求Hands | 接受并加界限 | 最近实际见手+接近轨迹后，可用Pose腕完成200ms保持；长期没见手不能新建增强，整个腕丢300ms退出。正面缩短投影允许小邻域候选，仍仅是意图估计 |
| 低频速度窗只剩当前点 | 接受 | 至少前后两个有效样本、350ms最大间隔，时间拟合；10/7.7/6.25Hz构造挥动检查；缺手即清轨迹，防重获跳点 |
| 蓄势超时从ARMED而非开始运动算 | 接受 | 保持蓄势不反复失败；挥动计时从实际运动起算，仍保留冷却/负例/跳点拒止 |
| 真正拍掌也应碎镜 | 调整 | 低帧率重叠可能不可观测，不能保证。改在实际双手可见、快速收缩且已相近时触发，引导“合到一拳距离，无需拍掌”；丢手/外推/重获本身不能触发 |
| 左右臂各自校准、正面角度门槛 | 接受并保留风险 | 独立存储端点；可用Hands不再受弱Pose肘误杀，角度仍要可靠Pose世界坐标。加入中值/限速/死区和缓降，代价是滞后，未做真人对比，不宣称已解决单目深度 |
| 手掌变大即满强度（更早建议） | 不采用 | 掌朝向和距离都能改变大小；不用伪深度填补角度失效 |
| 卡片要求重建目录/每帧包装FBO | 不照搬 | 保留现有工程与Qt FBO/尺寸检查；扩展纯特征/控制/星环模块是为可测试性，非另起工程 |

用户新要求优先于旧方案：开始施法后支持手自由；放下施法手收阵；握拳停法留阵；增强110–150%。近手关联、过严召唤范围和视觉微弱也已修改，但尚待本人在v0.2.0复验。没有完成真人动作验收、长时测试或最终课程报告。

## 这次只审三个问题

1. `features.py`/`control.py` 的身份关联、角度可靠性、中值/限速、左右校准是否仍会造成交叉换手或“稳定但迟钝”？给最小构造轨迹与真人失败判据。
2. `star_ring.py` 在支持手自由后，近期可见+Pose回退、透视缩短候选和退出条件，是否可能误进或无限保留增强？重点看遮挡、慢握、重新接近。
3. `interaction.py` 的B/C在10Hz附近、停留蓄势、缺手后重获、慢合与可见快合中，是否还有吞动作/误攻击？给具体时间序列，不建议外推缺失手来触发。
