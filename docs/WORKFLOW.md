# 工程协作与每轮交付约定

用户于2026-11-07明确补充。本约定适用于持续迭代和聊天恢复，与当前状态入口 [HANDOFF.md](HANDOFF.md) 配合使用。

## 职责

Codex 是主要实现者和唯一默认集成者：读取当前代码、最新反馈，作技术判断，完成实现、调试、相关测试、实际程序检查、打包及既有授权范围内的发布。独立可做的工作持续推进，不因非阻塞审查或发布故障停止全部工程工作。

Gemini 负责独立审查、视觉建议和边界明确的实现候选。意见需结合源码与证据核实，由Codex决定接受、调整、不采用或延期，不能照单全收或把技术争议转交用户裁决。

用户负责转交材料、真实摄像头动作和视觉/使用反馈。Codex不要求用户手工组织源码、提取日志、编写审查问题或承担可由代码和测试解决的判断。

## 每轮固定流程

1. 根据用户最新反馈和Gemini意见核实具体问题，读取实际代码、日志与证据，保留已完成成果。后来的明确需求高于初始方案；只按具体缺口分段读取旧聊天。
2. 实现必要修改，运行相关测试及实际程序检查；记录改动、失败、修正和结果。不能从单元测试通过推断真实识别/审美。
3. 给出明确可运行版本、启动入口及简短自测，分别列出软件已验证、真人待验证、未完成和已知限制。未改运行代码时沿用核验包体，不为文档更新重建同版。
4. 自动整理“发给Gemini”审查包与可粘贴提示词：固定版本/提交、相关源码或差异、需求变更、测试证据、已知问题，以及最多三个本轮重点问题。构造画面明确标记，不默认公开个人录像或原始动作日志。
5. 明确告诉用户上传哪个实际路径的文件、粘贴哪个文本全文。另一聊天不能访问本机路径时上传包，不让用户自行挑源码或日志。
6. 收到Gemini回复后逐项记录“接受/调整/不采用/延期”、依据、文件位置、最小复现、处理结果与验证。可解决的技术问题由Codex修复并重新交付。
7. 仅在确实依赖真实动作、审美、缺失资料或授权时等待用户；其他独立工作继续。远程发布故障不妨碍本地运行和审查交付。

## 日志与真实测试

用户在程序内点“记录日志”开始/停止，测试后只需回复法术、动作/现象与大致时段。Codex主动从 `%LOCALAPPDATA%\MirrorMoon\diagnostics` 找到对应日志、核对app_version、分析特征/时序并提取最小复现。用户不必寻找、筛选或打包日志。

原始动作关键点不加入公共仓库或公共审查包；对外提供经检查的摘要、脱敏最小回放或非个人构造输入。需要个人影像时另行明确范围。

单元测试、构造画面、图形运行、摄像头连通、带意图标签的真人动作、审美和长时稳定性分别记录。既有证据与本轮重跑分开；未运行不得写通过。

## 授权与发布恢复

“不重复构建或上传”指不重做已完成且校验一致的步骤，不是停止剩余工作。先核对已有release/草稿、附件和摘要；复用原发布，只补缺失步骤。已有授权的继续，确实缺授权时指出具体动作、目标和后果。

当前v0.4.0续发依据：旧聊天 `01a1b1c6-1084-7712-827d-43aa06700b13` 中，用户要求解决队友在GitHub看不到EXE的问题，并要求继续完成先前任务；2026-11-07本聊天又明确要求完成既有授权的缺失步骤。范围是复用既有草稿，补齐Windows附件并公开为预发行；不包含强推、删除历史发布或公开个人数据。

固定发布/包体/审查基线后，不覆写同名版本藏入后续运行修改。协作/交接文档另作提交，已发布标签和三个ZIP保留。已有审查包满足需求时保持字节不变，配套转交说明可单独更新；新运行修改使用新版本与新证据。

## 交接必填

HANDOFF至少包括：

- 最新用户需求及应保留的产品行为；
- 当前运行/审查版本、固定提交、分支和后续文档变化；
- 实际仓库、启动入口、依赖、日志、交付包、审查包与提示词路径；
- 已验证的方法/原始证据、本轮是否重跑、真人待验证与未完成；
- 发布链接、标签/基线、release ID、附件完成状态和校验；
- Gemini是否已转交/收到回复、逐项处置进度；
- 用户下一步、Codex下一步及确实依赖用户的工作。

交付当前轮后持续根据反馈迭代；不能把一次文件核对或已有源码包当最终验收。
